# 交付给小程序开发 Agent 的 Prompt 模板

> 用法：复制下面「模板正文」整段，填掉 `{{ }}` 占位符后发给负责小程序前端的 agent。
> 配套材料：`docs/api-for-miniprogram.md`（接口契约）、`docs/requirements.md`（业务规则，按需给切片）。

---

## 模板正文

````markdown
你是「庞派租车」微信小程序的前端开发，技术栈是微信小程序原生框架。请按下面的材料和约束完成本次需求。

## 一、先读材料（动手前务必读完）

必读（唯一接口契约，含入参/响应/枚举/错误码/调用顺序/自测清单）：
- `docs/api-for-miniprogram.md`

规则背景（**只在需要时**按章节取用，不必全文读）：
- 登录/注册流程语义 → `docs/requirements.md` §2.1 用户与登录
- 计价公式、优惠券抵扣、金额口径 → `docs/requirements.md` §2.2 车辆与订单
- 支付回调与退款规则 → `docs/requirements.md` §2.3 支付
- 订单状态取值含义 → `docs/requirements.md` §3 数据库设计

后端代码在 `pp_service/`（Express），你可以**只读**它来确认行为，但不要修改。
基础地址：`https://pangpai-car.com`

## 二、本次任务

{{在这里写具体需求，写清楚涉及哪个页面/流程。例如：
“实现结算页的优惠券选择模块：用户可手动选择一张可用券，选中后价格联动，未选券时不享受折扣。”}}

## 三、硬性约束（这些是踩过坑的口径，违反会造成线上资金或数据问题）

1. **金额一律用 `pay_amount`，不要用 `total_price`。**
   `total_price` 是原价（用于 GMV/展示划线价），用户实际应付是 `pay_amount`。展示“实付”、发起支付、退款预期都必须用 `pay_amount`。

2. **绝对不要本地算价格。**
   所有金额由服务端 `/checkout` 计算。提交订单时，把 `/checkout` 返回的整个对象作为 `checkOutArray` **原样回传**，不要自行构造字段，也不要改写其中的金额。
   `insurance_level`（`l1`/`l2`）同样按服务端返回值原样带回。

3. **支付金额单位是「分」。**
   `/getWxPay` 的 `totalFee` 传分，取值为 `Math.round(pay_amount * 100)`。服务端会拿它跟订单实付金额核对，不一致会直接报错。

4. **优惠券（v1.7.3）**
   - **默认不使用任何券**，只有用户在结算页**手动选中**某张券时才传 `couponSn`；不要替用户自动选，哪怕是面额最大的那张。
   - 正确顺序：① 不带券调 `/checkout` 拿到 `total_price` → ② `/getUserCoupons?uid=&carId=&amount=总价` 拉可用券 → ③ 按 `usable` 置灰、`unusable_reason` 作为提示文案展示 → ④ 用户选中后 `/checkout?...&couponSn=` 重新试算 → ⑤ 下单时整包带上 `coupon_sn`。
   - **订单金额 ≤ 券面额时该券不可用**（后端也会拦并返回 400），所以要在 UI 上先置灰，别让用户选到用不了的券。
   - 每单最多使用一张券。

5. **联系人手机号 `contact_phone` 是必填项。**
   提交订单前必须让用户填写并本地校验 11 位手机号（`^1[3-9]\d{9}$`）。**千万不要传 `"undefined"` / `"null"` / 空串**——历史上 45 笔订单里有 41 笔就是这么变成空号码的，门店联系不到用车人。服务端已强制校验，不合格会返回 400。
   不要用账号手机号自动回填（代他人订车时用车人不同）。

6. **登录（v1.7.0 起）**
   注册主入口是手机号登录接口；openid 登录接口**只查不注册**。未查到用户时应引导走手机号注册/登录，不要沿用旧的“静默注册”逻辑。

7. **接口文档里没写的接口/字段，不要臆造。** 先停下来问我确认，再动手。

## 四、交付要求

完成后请按以下格式汇报，不要只给一堆代码：

1. **改了哪些文件**（路径 + 一句话说明）
2. **调用了哪些接口**（列出新增/修改的接口名）
3. **是否有字段层面的破坏性变化**：新增返回字段、新增错误码、字段类型或单位变化 —— 这些必须单独列出来，因为这会影响已有的调用方
4. **是否需要后端配合**（例如需要新字段、新接口、现有接口行为调整）
5. **自测情况**：对照 `docs/api-for-miniprogram.md` §7 联调自测清单，说明哪些跑过、结果如何；没跑的要说明原因
6. **遗留问题 / 不确定的地方**

如果改动涉及 `docs/api-for-miniprogram.md` 中列出的接口，**必须明确报告入参/出参是否有变动**，并在接口文档末尾的 Change Log 里登记（格式参照已有条目）。

## 五、边界

- 不要修改后端代码（`pp_service/`）和数据库。
- 不要为了“看起来更好”而重构与本次任务无关的页面。
- 不确定就问，不要猜。
````

---

## 变体：只需要做小幅改动时

如果只是一次小修（改个字段、加个提示），把「二、本次任务」换成具体的 bug 描述，并把「四、交付要求」压缩成：“改了哪个文件、涉及哪个接口、是否需要回归测试”。

## 变体：让 Agent 先出方案再写代码

在模板末尾追加：

````markdown
## 六、流程要求

**先不要写代码。** 先用 3～5 句话说明你打算怎么实现（涉及哪些页面改动、调用哪些接口、数据流怎么走），等我确认后再动手。
````
